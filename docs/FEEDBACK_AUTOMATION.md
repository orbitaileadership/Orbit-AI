## Candidate changes and real local checks

Prepare in a separate detached worktree from the source HEAD. The controller and candidate manifest must agree on the base. Dirty proposal target files are refused rather than overwritten. Existing source work stays intact.

```powershell
node scripts/feedback/candidate.mjs prepare --repo . --run .feedback-runs/native/candidate-review --patch .feedback-runs/native/proposal.patch --reason "Concrete reason from optimizer"
node scripts/feedback/candidate.mjs verify --candidate .feedback-runs/native/candidate-review/candidate --run .feedback-runs/native/candidate-review --checks diff,syntax,lint,typecheck,test,build
```

Choose a unique candidate-review directory for each loop, such as loop-0001-candidate. Set report.candidateArtifactsDir to that path relative to the native run, report.candidateRepo to its absolute candidate worktree path, and each change.patchFile to loop-0001-candidate/candidate.patch. Deleted files use afterSha256: null. The controller reads actual candidate-test results rather than trusting caller-supplied pass claims. An existing trusted `node_modules` may be supplied with `--dependencies`; no package install occurs. Missing dependencies produce BLOCKED, not PASS. The candidate verifier strips credential environment variables, excludes real `.env` files and guards Node outbound network requests. This is defense in depth for trusted repository tests, not a sandbox for hostile patches or subprocesses. Inspect proposed code before testing. Never run migrations or `eval:quality`. Keep provider calls mocked; do not give candidate tests production credentials.

Use `candidate-tests.json` to map check statuses: passed→pass, failed→fail, blocked/skipped→not_run, preserving the exact command and reason. Proposed changes cannot be reported as verified when required checks are blocked. Do not alter a candidate after tests; if altered, rerun affected checks and independent review. Preparing this disposable candidate is authorized; changing the working website still needs approval.

For a no-change pass use `decision: "continue"`. A failed/blocked proposal must be corrected and re-reviewed rather than relabeled passing. Approval references are audit records, not a technical substitute for consent.

For apply: verify the frozen candidate/report still match; apply only the exact reviewed patch to the isolated source worktree; stage/commit only its approved paths and preserve all other staged, tracked and untracked work. Do not mark skipped or unexecuted checks passed. An independent reviewer must inspect the apply diff and results.
